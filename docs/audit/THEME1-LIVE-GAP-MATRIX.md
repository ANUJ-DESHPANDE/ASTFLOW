## PRE-IMPLEMENTATION FINDINGS (this session, per continuation prompt section 27)

**Already complete:** official MTEB integration and its regression test; positive-IDF BM25 with case/underscore-aware tokenization; version-aware indexing with immutable per-snapshot caches; content-hash embedding reuse across versions (added last session on this branch, now also unit-verified); the retrieval-only scope boundary (no generation) is correctly respected end to end.

**Partially complete:** BM25 field weighting exists nowhere (single merged text field, both in the JS product chunker and the official dataset adapter) but has never been tested as a hypothesis, so "missing" would overstate it — it's *untested*, not *broken*. Agentic refinement is real but its benefit is only measured on a tiny 16-query local fixture, not on AppsRetrieval.

**Actually missing:** a held-out development/validation split (did not exist before this session; now built as tooling, not yet run against real data). Evolutionary/all-version retrieval (bonus) — confirmed still absent, unchanged.

**Broken:** none found in the retrieval path itself this session. (Two frontend bugs were found and one fixed in the immediately preceding session on this branch — see `docs/audit/BUGS.md` B16/B17 — unrelated to retrieval.)

**Not worth implementing (yet):** BM25F, k1/b changes, a reranker, or any semantic-model swap — all explicitly forbidden by the prompt to attempt before measurement, and measurement was blocked this session by network policy, not by any decision to skip it.

**Retrieval bottleneck, best guess pending real data:** the historical low absolute NDCG@10 (0.061 BM25 / 0.088 hybrid) most plausibly reflects a fundamental mismatch — general-purpose BM25/MiniLM against a Python competitive-programming corpus with long documents (truncation risk, unmeasured this session) and a query style AppsRetrieval doesn't clearly document — rather than a single fixable bug. This is a hypothesis, not a finding; `benchmark/analyze_corpus.py`'s token-length output is the first real evidence needed to confirm or reject the truncation half of it.

**Proposed experiment order once the dataset is reachable (matches prompt section 26):**
1. `python -m benchmark.build_dev_split` — one-time, produces `benchmark/dev_split.json`.
2. `python -m benchmark.analyze_corpus` — token-length distribution + token document-frequency, no qrels touched, safe to run any number of times.
3. `python -m benchmark.tune_bm25` — k1/b grid search on `dev_query_ids` only; review the printed table before touching code.
4. If a config clearly wins on dev, confirm once: `python -m benchmark.tune_bm25 --confirm --k1 <best> --b <best>`.
5. Only if confirmation holds up, change the two lines in `backend/app/indexing/service.py` / wherever `Retriever(...)` is constructed for the product path to pass the new `k1`/`b`, and re-run the backend suite.
6. Repeat steps 2–5's spirit for the stopword hypothesis (`analyze_corpus.py`'s frequency table feeds a hand-picked `--stopwords-file` for `tune_bm25.py`); do not chain more than one or two hypotheses before stopping to document results, per the prompt's own anti-overfitting rules.
7. Only after a frozen BM25 (and, time permitting, fusion/dense) configuration is chosen from dev results does an official `run_mteb.py` run become worth its ~2.5 minutes (BM25) or much longer (hybrid) cost — and only once, not per experiment.
